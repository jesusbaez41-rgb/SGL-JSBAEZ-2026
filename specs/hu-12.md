# HU-COM-12 — Auditoría y trazabilidad inmutable

**Código:** HU-COM-12  
**Módulo/Épica:** Auditoría y Seguridad  
**Entorno:** Plataforma Web + Servidor Central (Backend + PostgreSQL)  
**Prioridad:** Must Have  
**Estimación:** 5 SP  
**Estado:** Implementada  
**Fecha:** 2026-11-15

## 1. Objetivo

Permitir que el Administrador Técnico (y el Administrador Académico) consulte
el registro de auditoría de las acciones administrativas, y garantizar que el
backend registre de forma inmutable todas las acciones críticas.

## 2. Alcance

Incluye:

- Consulta paginada de `auditoria` con filtros por acción, entidad, usuario,
  laboratorio, equipo, rango de fechas y texto del detalle.
- Contexto consultable: actor, fecha/hora, acción, entidad, laboratorio,
  equipo, IP y detalle JSON.
- Inmutabilidad en tres capas: API sin rutas de modificación, triggers de BD
  para `UPDATE`/`DELETE`/`TRUNCATE`, y rol de aplicación sin privilegios de
  modificación sobre `auditoria` ni `evento_autenticacion`.
- Registro automático de las acciones críticas existentes (laboratorios,
  equipos, aplicaciones, vínculos, permisos, despliegues, políticas, usuarios
  y grupos).
- UI con pestañas **Acciones administrativas** y **Accesos**, filtros,
  paginación y visor de detalle.

No incluye (depende de otras HU):

- Auditar listas blancas: la funcionalidad de RN-016 todavía no está
  implementada (módulo `whitelists`).
- Auditar el logon de la PC en SGL: depende de HU-COM-01.

## 4. Modelo de datos

### `auditoria` (ampliada)

| Columna | Tipo | Uso |
|---|---|---|
| `id` | UUID | PK |
| `usuario_id` | UUID NOT NULL | Actor responsable (FK a `usuario`) |
| `accion` | VARCHAR(32) | `CREAR`, `ACTUALIZAR`, `ELIMINAR`, `DESPLEGAR`, `CAMBIO_PERMISO`, `EJECUTAR` |
| `entidad_afectada` | VARCHAR(64) | `usuario`, `grupo`, `laboratorio`, `equipo`, `aplicacion`, `vinculo_app_lab`, `despliegue`, `politica`, `permiso_app_grupo` |
| `entidad_id` | UUID | Identificador de la entidad |
| `laboratorio_id` | UUID | Laboratorio afectado (nuevo, CA-02) |
| `equipo_id` | UUID | Equipo afectado (nuevo, CA-02) |
| `detalle` | JSONB | Detalle libre de la operación |
| `ip_origen` | VARCHAR(45) | IP del actor |
| `fecha_evento` | TIMESTAMPTZ | Fecha/hora |
| `inmutable` | BOOLEAN | Siempre `TRUE` |

Las columnas `laboratorio_id`/`equipo_id` **no tienen FK**: la auditoría debe
conservarse aunque se elimine el laboratorio o el equipo. El join devuelve
`null` si la entidad ya no existe, pero el `detalle` y el ID quedan en el
registro.

Índices: `usuario_id`, `(entidad_afectada, entidad_id)`, `fecha_evento DESC`,
`laboratorio_id`, `equipo_id`.

### Inmutabilidad

```sql
tg_auditoria_block_update    BEFORE UPDATE   -> excepción
tg_auditoria_block_delete    BEFORE DELETE   -> excepción
tg_auditoria_block_truncate  BEFORE TRUNCATE -> excepción
```

Los triggers se recrean en la migración 10 para que una instalación nueva
también los tenga. La migración desactiva temporalmente solo el trigger de
`UPDATE` para rellenar `laboratorio_id`/`equipo_id` de las filas históricas y
lo vuelve a activar.

### Rol de aplicación

- `sgl_app` es un rol **sin superusuario** y sin ownership de las tablas.
- Tiene `SELECT, INSERT, UPDATE, DELETE` sobre el resto del esquema.
- Sobre `auditoria` y `evento_autenticacion`: **solo `SELECT, INSERT`**.
- `sgl_user` (superusuario) queda reservado para migraciones y mantenimiento.
- El backend conecta con `DATABASE_URL=postgres://${DB_APP_USER}:${DB_APP_PASSWORD}@db:5432/${POSTGRES_DB}`.

## 5. API

### `GET /api/audit/logs`

Permiso: `audit:read` (Admin Académico y Admin Técnico).

| Parámetro | Tipo | Descripción |
|---|---|---|
| `limit` | int 1..200 (50) | Tamaño de página |
| `offset` | int >= 0 | Desplazamiento |
| `accion` | enum | Acción de auditoría |
| `entidad` | string <= 64 | Entidad afectada |
| `usuario` | string <= 120 | uid o nombre completo (ILIKE) |
| `laboratorio_id` | UUID | Laboratorio afectado |
| `equipo_id` | UUID | Equipo afectado |
| `desde` | fecha ISO | Desde (inclusive) |
| `hasta` | fecha ISO | Hasta (inclusive; si es `YYYY-MM-DD`, fin del día) |
| `q` | string <= 120 | Búsqueda en acción/entidad/detalle/usuario |
| `excluir_sincronizacion` | 0/1 | Oculta las sincronizaciones de inventario |

Respuesta:

## 8. Registro automático y contexto

`recordAuditEvent(req, { accion, entidad, entidadId, detalle, laboratorioId, equipoId })`:

- Exige actor (`req.user.id`); si falta, loguea el error y no inserta.
- Deriva el laboratorio de `laboratorioId`, de `detalle.laboratorio_id` o de
  `entidad === 'laboratorio'`.
- Deriva el equipo de `equipoId`, de `detalle.equipo_id` o de
  `entidad === 'equipo'`.
- Descarta identificadores que no sean UUID para no perder el evento por una
  FK inválida.
- La sincronización periódica de MeshCentral se marca con
  `detalle.origen = 'SISTEMA'` y `detalle.automatico = true`. Las corridas
  automáticas sin cambios no generan registro. La sincronización manual queda
  como `origen = 'USUARIO'`.

## 11. Configuración

En `.env` (permisos `600`, no versionado):

```ini
DB_APP_USER=sgl_app
DB_APP_PASSWORD=...
```

`docker-compose.yml` usa esos valores para `DATABASE_URL`. Para aplicar la
migración y configurar el password del rol:

```bash
sudo bash /opt/sgl-web/scripts/bootstrap-hu12.sh
docker compose up -d backend
```

El script es idempotente: aplica `db/migrations/10-hu12-auditoria.sql` y
ejecuta `ALTER ROLE sgl_app PASSWORD`.

## 13. Dependencias y pendientes

- **RN-016 (listas blancas):** cuando se implemente el módulo, cada alta/baja
  debe llamar a `recordAuditEvent` con `entidad: 'lista_blanca_url'`.
- **HU-COM-01 (logon de PC):** el registro de sesión de PC debe auditarse con
  el mismo helper.
- **Superusuario:** `sgl_user` puede deshabilitar triggers por ser owner y
  superusuario; por eso el backend ya no lo usa. El acceso al superusuario
  queda restringido a migraciones/mantenimiento y a la red interna de Docker.
