# HU-COM-09 — Control de navegación por listas blancas de URLs

**Código:** HU-COM-09
**Módulo/Épica:** Filtrado de navegación
**Entorno:** Plataforma Web + PC Cliente Windows + Servidor Central (Backend + Squid + MeshCentral)
**Prioridad:** Must Have
**Estimación:** 8 SP
**Estado:** Implementada (verificación en PC pendiente)
**Fecha:** 2026-11-19

## 1. Objetivo

Permitir que el Administrador Académico / Técnico defina la **lista blanca de
URLs de cada grupo** y que las PCs de los laboratorios apliquen ese filtro,
de modo que un estudiante solo navegue por la **unión** de las listas de sus
grupos y todo lo demás quede bloqueado (RN-016).

**Como** Administrador Académico / Técnico
**Quiero** cargar dominios permitidos por grupo y desplegar la configuración de
filtrado a las PCs
**Para** garantizar que los estudiantes solo accedan a los sitios autorizados
para sus grupos, sin posibilidad de evadir el filtro por IP directa, proxy no
autorizado o VPN.

## 2. Alcance

Incluye:

- Alta, edición, baja lógica y consulta de dominios por grupo
  (`lista_blanca_url`), con normalización y validación estricta.
- Cálculo de la **lista efectiva** de un estudiante como unión de los dominios
  activos de todos sus grupos (RN-016).
- Generación del `squid.conf` global del proxy con ACLs por IP de origen y por
  grupo, más el snippet por grupo en formato Squid y SquidGuard (CA-07).
- Publicación del script de PC (`sgl-navegacion.ps1`) y del PAC
  (`sgl-proxy.pac`) en `/instaladores` para que las PCs los descarguen.
- Registro de la **sesión del estudiante en la PC** (hostname, SID e IP) para
  aplicar el filtrado por grupo (CA-04).
- Despliegue de la configuración por laboratorio vía MeshCentral (CA-01,
  CA-08) y redespliegue automático al cambiar una lista (CA-09).
- Bloqueo local en la PC: firewall por SID de estudiante para impedir salida
  directa a Internet, QUIC, DNS externo y VPN (CA-03, CA-05, CA-06).
- Exención del administrador local (`S-1-5-32-544`) para no romper la operación
  ni la administración del equipo.
- Auditoría de todas las acciones críticas (RN-010).
- Pantalla **Listas blancas** con dominios por grupo, estado del proxy,
  configuraciones generadas y despliegue por equipo.

No incluye:

- Inspección de contenido, antivirus o proxy transparente: el filtrado es por
  dominio (no por URL completa ni por categoría).
- Bloqueo de aplicaciones (HU-COM-06) o instalación de software (HU-COM-08).
- Autenticación del proxy con credenciales de dominio: se identifica al
  estudiante por la IP de origen informada en el logon de la PC.

## 4. Arquitectura

```
┌────────────┐  logon (SID, hostname, IP)   ┌──────────────┐
│ PC alumno  │ ───────────────────────────▶ │  Backend SGL │
│            │   POST /api/navigation/session│              │
│            │ ◀─────────────────────────── │  unión de    │
│            │   proxy + dominios permitidos │  listas      │
└─────┬──────┘                              └──────┬───────┘
      │ navega solo por proxy                      │ escribe
      ▼                                            ▼
┌──────────────┐  squid -k parse + reload  ┌──────────────────┐
│  sgl-squid   │ ◀─────────────────────── │ sgl-squid.conf   │
│ (contenedor) │  timer cada 10 s          │ (publicado)      │
│    :3128     │                           └──────────────────┘
└──────────────┘
```

1. El administrador carga dominios por grupo en la UI o por API.
2. El backend normaliza, valida y guarda en `lista_blanca_url`; luego regenera
   `sgl-squid.conf` y lo publica en `/opt/sgl-instaladores`.
3. `google.com` se agrega siempre a la lista efectiva de cualquier grupo
   (`DOMINIOS_BASE` en `whitelists.config.js`); un estudiante sin grupo sigue
   sin navegación (RN-016).
4. El sincronizador valida el candidato dentro del contenedor
   (`docker exec sgl-squid squid -k parse -f /sgl/sgl-squid.conf`) y solo
   entonces escribe la configuración viva y ejecuta `squid -k reconfigure`.
   Una configuración inválida nunca deja el proxy caído.
4. Al iniciar sesión, el script de la PC informa hostname, SID e IP. El backend
   resuelve el equipo y el usuario, calcula la unión de listas de sus grupos y
   guarda la sesión; el Squid se regenera con la IP de esa PC en la ACL de cada
   grupo.
5. Las reglas de firewall del script (modo SYSTEM) impiden que el estudiante
   salga a Internet sin pasar por el proxy.

## 7. Reglas de filtrado y anti-evasión

### 7.1 Squid (servidor)

- `http_port 192.168.100.58:3128`, `cache deny all`.
- `happy_eyeballs_connect_timeout 250 milliseconds` y `connect_timeout 10
  seconds`: el host no tiene ruta IPv6, así que si un dominio publica `AAAA`
  Squid prueba IPv4 en paralelo en lugar de quedarse esperando.
- **Deny by default**: la última regla es `http_access deny all`.
- Solo se permite `http_access allow <acl_src_grupo> <acl_dst_dominios>` para
  las IPs de PCs con una sesión activa cuyo grupo tiene lista blanca.
- Se rechaza el acceso por **IP literal** con `acl sgl_numeric_host
  dstdom_regex` y `http_access deny sgl_numeric_host` (CA-03).
- Se rechaza `CONNECT` fuera del puerto 443 y `to_localhost`.
- Los recursos internos (`.clockwork.local`, `.local` y la subred del
  laboratorio) siguen disponibles (RN-016).
- Un estudiante **sin grupo** no recibe ninguna regla `allow`: no navega.

### 7.2 PC del estudiante (modo SYSTEM)

El script `sgl-navegacion.ps1 -Modo Firewall` corre al arrancar como SYSTEM y
crea reglas de salida **por SID de cada estudiante SGL**. Windows Firewall
rechaza un SID suelto en `-LocalUser` (`HRESULT 0x80070057`), así que el script
lo convierte al formato SDDL `D:(A;;CC;;;<SID>)`; por eso el backend incluye en
el script a los estudiantes activos con `samba_sid` en los grupos del
laboratorio (son las cuentas que realmente inician sesión en la PC):

| Regla | Protocolo / puerto | Destino |
|---|---|---|
| Web | TCP 80, 443, 8080, 8443 | `Internet` |
| QUIC | UDP 443 | `Internet` |
| DNS externo | UDP/TCP 53 | `Internet` |
| VPN | UDP 500, 4500, 1194, 51820 | `Internet` |
| VPN PPTP | TCP 1723 | `Internet` |
| Proxy SGL | TCP 3128 | `192.168.100.58` (permitido) |

Cada alta va en `try/catch -ErrorAction Stop`: si una regla falla se registra
`error al crear las reglas para <SID>` y el resumen `firewall de navegacion
aplicado a X de Y usuario(s)`, de modo que el log nunca declara un éxito falso.

`-RemoteAddress Internet` excluye las subredes locales, por lo que la PC sigue
accediendo al proxy y a los recursos internos. El SID de administradores
(`S-1-5-32-544`) no se incluye en las reglas: la administración del equipo no
se bloquea.

### 7.3 PC del estudiante (modo usuario)

Al iniciar sesión, el script:

1. Si el usuario pertenece a `S-1-5-32-544`, quita el proxy y sale (exención
   de administrador).
2. Si no pertenece a ningún grupo SGL, no configura proxy.
3. Si pertenece, informa la sesión al backend y configura `ProxyEnable`,
   `ProxyServer` y `ProxyOverride` en `HKCU`.
4. Si el registro de la sesión falla, **no** configura el proxy (fail-closed):
   sin proxy, el firewall igualmente impide la salida directa.

## 10. Operación

```bash
# Instalación inicial (host, como root)
cd /opt/sgl-web
sudo ./scripts/install-squid-hu09.sh

# Estado del proxy (contenedor) y del sincronizador
docker ps --filter name=sgl-squid
systemctl status sgl-squid-sync.timer
docker exec sgl-squid squid -k parse -f /etc/squid/squid.conf

# Log de accesos permitidos/denegados
docker exec sgl-squid tail -f /var/log/squid/access.log
```

```
NAV_PROXY_HOST=192.168.100.58
NAV_PROXY_PORT=3128
NAV_API_BASE=http://192.168.100.58:8080/api
NAV_AGENT_KEY=<clave compartida con el agente>

```

## 11. Limitaciones conocidas

1. **Identificación por IP informada:** el agente envía hostname, SID e IP. Un
   estudiante con conocimientos podría intentar falsear el SID para que se le
   aplique la lista de otro grupo. El impacto está acotado a grupos
   registrados y el firewall igualmente impide la salida directa.
2. **Clave del agente en el script:** `NAV_AGENT_KEY` viaja en
   `sgl-navegacion.ps1`. Debe rotarse si se filtra y el script se sirve por
   HTTP interno.
3. **Filtrado por dominio:** no inspecciona rutas ni contenido; un dominio
   permitido puede alojar contenido no deseado.
4. **Reglas por SID de usuario:** Windows Firewall no acepta SIDs de grupo en
   `-LocalUser` (solo SDDL de usuarios), por lo que el firewall se aplica a los
   estudiantes con `samba_sid` registrado. Un estudiante de AD creado fuera del
   sistema (sin `samba_sid`) no recibe reglas hasta la siguiente generación.
4. **HTTPS:** Squid filtra por `CONNECT` al dominio, sin interceptar TLS
   (no hay MITM ni certificado raíz).
5. **Sesión vigente por horas:** una sesión se considera activa durante
   `NAV_SESSION_HOURS` (12 por defecto); si la PC no cierra sesión, la regla
   persiste hasta ese límite.
