# HU-COM-08 — Despliegue remoto de aplicaciones

**Código:** HU-COM-08  
**Módulo/Épica:** Gestión de Aplicaciones y Despliegue  
**Entorno:** Plataforma Web + Servidor Central (Backend + MeshCentral) + PC Cliente Windows  
**Prioridad:** Must Have  
**Estimación:** 8 SP  
**Estado:** Implementada  
**Fecha:** 2026-11-12

## 1. Objetivo

Disparar la instalación o desinstalación masiva de una aplicación en todas las
PCs de un laboratorio. El backend valida el vínculo app-laboratorio, envía la
orden silenciosa a cada equipo mediante MeshCentral y registra el estado
individual de cada PC.

**Como** Administrador Técnico  
**Quiero** disparar instalación o desinstalación masiva de una aplicación en
todas las PCs activas de un laboratorio, y que el backend orqueste el despliegue
vía MeshCentral y la PC ejecute el comando  
**Para** automatizar el mantenimiento de software sin instalación manual.

## 2. Alcance

Incluye:

- Despliegue masivo por laboratorio (RN-003).
- Validación del vínculo app-laboratorio antes de desplegar (CA-05, RN-002).
- Envío de la orden silenciosa a MeshCentral (CA-06, CA-09, CA-10).
- Estado individual por equipo: PENDIENTE, EN_PROCESO, COMPLETADO, FALLIDO
  (CA-03, RN-006).
- Equipos apagados: quedan PENDIENTE y se reintentan al encenderse o
  manualmente (CA-02, CA-08, RNF-005).
- Recepción del resultado desde el agente (CA-07, CA-11).
- Desinstalación remota (CA-04).
- Auditoría de cada disparo y reintento (RN-010).
- Pantalla **Despliegues** con listado, resumen por estado y detalle por equipo.

No incluye:

- Instalación **por usuario** (eso se resuelve con GPO, HU-COM-01).
- Selección de PCs individuales: el MVP despliega al laboratorio completo
  (RN-003).
- Persistencia del resultado de instalación en el equipo (RN-006 se cubre con
  el estado por PC del despliegue).
- Políticas de ejecución y bloqueo de aplicaciones (HU-COM-09/HU-COM-10).

## 4. Flujo de un despliegue

```
Admin Técnico (Web)
   │  POST /api/deployments {app_id, laboratorio_id, tipo}
   ▼
Backend SGL
   │  1. valida vínculo app-laboratorio            (CA-05 / RN-002)
   │  2. crea `despliegue` + una fila por equipo del laboratorio
   │  3. consulta el estado EN VIVO en MeshCentral
   │  4. despacha en paralelo a los equipos encendidos
   ▼
Bridge MeshCentral  (scripts/meshcentral-bridge.js)
   │  5. lanza la instalación DESACOPLADA:
   │     - la PC descarga el instalador por HTTP desde SGL
   │       (http://<servidor>:8080/instaladores/<archivo>)
   │     - ejecuta el instalador en modo silencioso
   │     - escribe el código de salida en un archivo temporal
   ▼
PC cliente (agente MeshCentral como servicio LocalSystem)
   │  6. descarga, instala y reporta SGL_EXITCODE=<codigo>
   ▼
Backend SGL
   7. consulta el archivo de resultado y actualiza el estado por equipo
```

### Por qué el instalador se descarga por HTTP

El comando `meshctrl Upload` de MeshCentral **no funciona** con el agente de
este laboratorio: la sesión de subida se cierra ("Connection Closed") y el
archivo nunca llega a la PC. Además, el agente tiene **un solo slot de
comandos**: si un instalador se cuelga, rechaza todo lo demás sin responder
(`Run commands cannot execute, already busy`).

Por eso el despliegue:

1. Publica los instaladores en `/instaladores/` (nginx, solo lectura).
2. La PC los descarga con `Invoke-WebRequest` desde la red del laboratorio.
3. La ejecución se lanza en un proceso aparte con `-EncodedCommand`, de modo
   que el agente queda libre en ~1 segundo.
4. El resultado se consulta con comandos cortos (`cmd /c type`) hasta que el
   instalador termina.

El paso 4 no espera la respuesta del equipo dentro del alta: por eso el
despliegue responde en menos de 2 segundos (CA-01) y el resultado se va
reflejando por equipo (CA-07).

### Fases visibles (CA-03)

| Fase | Significado |
|---|---|
| `ENVIANDO` | Se prepara el instalador para el equipo |
| `EJECUTANDO` | La PC descarga y ejecuta el instalador |
| `FINALIZADO` | Terminó (ver estado y salida) |
| `ESPERANDO` | El equipo está apagado; se reintentará |

## 5. API

| Método | Ruta | Permiso | Descripción |
|---|---|---|---|
| `GET` | `/api/deployments` | `deployments:read` | Lista los despliegues con el resumen de estados |
| `GET` | `/api/deployments/:id` | `deployments:read` | Detalle con el estado de cada equipo |
| `POST` | `/api/deployments` | `deployments:manage` | Crea y dispara un despliegue masivo |
| `POST` | `/api/deployments/:id/retry` | `deployments:manage` | Reintenta equipos pendientes o fallidos |

### Ejemplo de alta

```json
POST /api/deployments
{
  "app_id": "<app-id>",
  "laboratorio_id": "<laboratorio-id>",
  "tipo": "INSTALAR"
}
```

Respuestas:

- `201` con el despliegue y el estado inicial de cada equipo.
- `409 APP_NO_VINCULADA` si la aplicación no está vinculada al laboratorio
  (CA-05 / RN-002).
- `400 DESINSTALACION_NO_DEFINIDA` si se pide una desinstalación de una app
  que no define comando y no es un `.msi` (CA-04).

### Reintento

```json
POST /api/deployments/<id>/retry
{ "equipo_id": "<equipo-id>" }   // opcional: reintenta solo ese equipo
```

Devuelve `{ reintentados, pendientes, despliegue }`. Solo se despachan los
equipos que MeshCentral reporta como encendidos; el resto sigue PENDIENTE.

## 6. Estados por equipo

| Estado | Significado |
|---|---|
| `PENDIENTE` | El equipo está apagado o el agente no está conectado; la orden se reintentará |
| `EN_PROCESO` | La orden se envió y se espera el resultado |
| `COMPLETADO` | El agente devolvió código de salida 0 |
| `FALLIDO` | El comando devolvió un código distinto de 0 o erroró |

Un equipo que estaba apagado **no** se marca como fallido: MeshCentral encola
la orden pero no la ejecuta, así que el backend lo mantiene en PENDIENTE
(CA-02) y el barrido periódico lo reintenta cuando el equipo vuelve a estar
en línea.

## 7. Reintento automático (CA-02)

Un job interno (`deployments.sync.js`) corre cada
`DEPLOYMENTS_RETRY_MINUTES` minutos (2 por defecto):

1. Busca las filas `PENDIENTE` de despliegues abiertos.
2. Consulta en MeshCentral si el equipo ya está en línea.
3. Si lo está, vuelve a despachar la orden e incrementa `intentos`.

El administrador también puede reintentar a mano desde la interfaz.

### Detección del tipo de instalador

No existe un flag silencioso universal. El bridge lee el archivo y elige los
parámetros según la firma del instalador:

| Tipo | Detección | Parámetros |
|---|---|---|
| MSI | extensión `.msi` | `msiexec /i … /qn /norestart` |
| NSIS | firma `Nullsoft` / `NSIS` | `/S` |
| Inno Setup | firma `Inno Setup` | `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART` |
| InstallShield | firma `InstallShield` | `/s /v"/qn"` |
| WiX Burn | firma `WixBundle` / `Burn` | `/quiet` |
| Desconocido | sin firma | `/S` (el más común) |

Si la aplicación define `parametros_silenciosos`, esos tienen prioridad sobre
la detección. Si el instalador se cuelga, se mata a los 3 minutos
(`MESH_INSTALL_TIMEOUT_MS`) y el resultado incluye `SGL_MOTIVO=TIMEOUT` para
que la interfaz indique que probablemente falten parámetros.

Verificado en el laboratorio con:

- **7-Zip 24.08 (MSI)** → `COMPLETADO`, instalado en `C:\Program Files\7-Zip`.
- **WinRAR 7.23 (EXE)** → `COMPLETADO`, instalado en `C:\Program Files\WinRAR`.
## 8. Desinstalación remota (CA-04)

- `tipo = DESINSTALAR`.
- Si la aplicación define `aplicacion.comando_desinstalacion`, se ejecuta ese
  comando PowerShell en el equipo.
- Si no lo define y el instalador es `.msi`, se usa `msiexec /x … /qn`.
- Si no lo define y no es `.msi`, el despliegue se rechaza con
  `400 DESINSTALACION_NO_DEFINIDA`.

## 9. Modelo de datos

No se agregan tablas: se reutilizan `despliegue` y `despliegue_equipo`.

### `despliegue`

- `id` UUID.
- `vinculo_id` → `vinculo_app_lab.id` (el despliegue siempre nace de un
  vínculo app-laboratorio, RN-002).
- `usuario_id` → `usuario.id` (quién lo disparó).
- `tipo` `INSTALAR` | `DESINSTALAR`.
- `fecha_inicio`, `fecha_fin`, `total_equipos`.

### `despliegue_equipo`

- `despliegue_id`, `equipo_id` (único por despliegue).
- `estado` `PENDIENTE` | `EN_PROCESO` | `COMPLETADO` | `FALLIDO`.
- `mensaje_error`, `intentos`, `fecha_reporte`.

### `aplicacion` (columna nueva)

- `comando_desinstalacion` TEXT — comando PowerShell de desinstalación
  (migración `db/migrations/06-hu08-deploy.sql`).

## 10. Integración con MeshCentral

El bridge (`scripts/meshcentral-bridge.js`) expone:

| Método | Ruta | Descripción |
|---|---|---|
| `GET` | `/devices` | Lista normalizada de dispositivos (estado, IP, usuario) |
| `POST` | `/subir` | Prepara el instalador y devuelve su URL de descarga |
| `POST` | `/ejecutar` | Lanza la instalación desacoplada en el equipo |
| `POST` | `/resultado` | Lee el código de salida de la instalación |
| `POST` | `/terminal` | Consola remota: ejecuta un comando y devuelve la salida |

`POST /ejecutar` recibe:

```json
{
  "nodeid": "node/mesh/…",
  "ruta_remota": "C:\\Windows\\Temp\\7-zip-24.08.msi",
  "url_descarga": "http://192.168.100.58:8080/instaladores/7-zip-24.08.msi",
  "tipo": "INSTALAR",
  "parametros": "/qn",
  "resultado_id": "<id de la fila despliegue_equipo>"
}
```

y responde de inmediato `{ ok: true, pendiente: true, resultado_id }`.

Reglas del bridge:

- El instalador se descarga por HTTP desde SGL; no se usa `meshctrl Upload`.
- La instalación se lanza en un proceso PowerShell aparte
  (`-EncodedCommand`), así el agente no queda bloqueado.
- El script remoto imprime `SGL_EXITCODE=<código>` en un archivo temporal;
  el backend lo lee con `POST /resultado` (CA-11).
- Los `.msi` se instalan con `msiexec /i … /qn /norestart`; los `.exe` con
  `Start-Process -WindowStyle Hidden` (CA-10).
- Si el agente está apagado, el bridge lo informa (`EQUIPO_APAGADO`) y el
  equipo queda PENDIENTE (CA-02).
- Timeout del instalador en el equipo: `MESH_INSTALL_TIMEOUT_MS` (3 min).

## 13. Interfaz

- **Despliegues:** listado con tipo, app, laboratorio, fecha, progreso y las
  etiquetas de estado por equipo.
- **Nuevo despliegue:** se elige el laboratorio y solo se listan las
  aplicaciones **vinculadas** a ese laboratorio; se elige instalar o
  desinstalar.
- **Detalle:** tabla con hostname, MAC, estado, intentos y mensaje; botón de
  reintento por equipo y reintento masivo. Mientras haya equipos sin estado
  final, la vista se refresca sola cada 3 segundos (CA-03, CA-07).
