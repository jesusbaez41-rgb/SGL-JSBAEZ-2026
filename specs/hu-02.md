# HU-COM-02 — CRUD y sincronización de cuentas de usuario con Samba AD

**Código:** HU-COM-02  
**Módulo/Épica:** Gestión de Usuarios y Autenticación  
**Prioridad:** Must Have  
**Estimación:** 8 SP  
**Estado:** Implementada  
**Fecha:** 2026-11-04

## 1. Objetivo

Permitir que el Administrador Académico y el Administrador Técnico creen,
consulten, actualicen y desactiven cuentas de usuario desde la plataforma web,
manteniendo sincronizados Samba AD (LDAP) y PostgreSQL.

## 2. Alcance

Incluye:

- Alta de cuentas en Samba AD y PostgreSQL.
- Consulta individual y listado.
- Modificación de nombre, correo, rol, estado y contraseña.
- Desactivación y reactivación de cuentas (sin borrado físico).
- Validación de unicidad de `uid` y `email` en BD y en el directorio.
- Sincronización LDAP por LDAPS con compensación ante fallos.
- Auditoría de alta y modificación en `auditoria` (RN-010).
- Cierre de sesiones web al desactivar una cuenta.

No incluye:

- Borrado físico de usuarios (la HU pide desactivación).
- Asignación de estudiantes a grupos ni docentes a grupos (HU de grupos, RN-012/RN-017).
- Cambio de `uid` después del alta (se mantiene inmutable para preservar el DN).
- Autoservicio de contraseña por parte del usuario.

## 3. Criterios de aceptación

| CA | Implementación | Evidencia |
|---|---|---|
| CA-01 Sincronización con Samba AD | Cada alta/edición/desactivación se aplica primero por LDAPS y luego en PostgreSQL, con compensación si falla la BD. | `backend/src/modules/users/users.service.js`, `backend/src/modules/auth/ldap.service.js` |
| CA-02 Asignación de roles | Solo se aceptan `ADMIN_ACADEMICO`, `ADMIN_TECNICO`, `DOCENTE`, `ESTUDIANTE`. | `users.validators.js`, `config/permissions.js` |
| CA-03 Unicidad de cuenta | `uid` y `email` se normalizan a minúsculas y se validan en PostgreSQL y en Samba AD antes de crear. | `users.service.js` (`assertNoDuplicates`), `usuario.uq_usuario_uid/email` |
| CA-04 Creación/Modificación/Desactivación | `POST /api/users`, `PATCH /api/users/:id`, `PATCH /api/users/:id/status`; LDAP `add` y `modify`. | `users.routes.js`, `ldap.service.js` |

## 4. API

| Método | Ruta | Permiso | Descripción |
|---|---|---|---|
| `GET` | `/api/users` | `users:read` | Lista usuarios. Docente solo sus estudiantes (RN-017). |
| `GET` | `/api/users/:id` | `users:read` | Consulta un usuario. Docente limitado a sus grupos. |
| `POST` | `/api/users` | `users:manage` | Crea la cuenta en Samba AD y PostgreSQL. |
| `PATCH` | `/api/users/:id` | `users:manage` | Actualiza nombre, correo, rol, estado y/o contraseña. |
| `PATCH` | `/api/users/:id/status` | `users:manage` | Activa o desactiva la cuenta. |

### Ejemplo de alta

```json
POST /api/users
{
  "uid": "jperez",
  "nombre_completo": "Juan Pérez",
  "email": "jperez@clockwork.local",
  "rol": "DOCENTE",
  "password": "SglDoc2026!x9"
}
```

### Ejemplo de modificación

```json
PATCH /api/users/<id>
{
  "nombre_completo": "Juan Pérez Gómez",
  "email": "jperez@clockwork.local",
  "rol": "DOCENTE",
  "activo": true,
  "password": "NuevaClave2026!x9"
}
```

## 5. Sincronización LDAP

### Alta (`CA-01`, `CA-04`)

1. Bind de servicio contra `ldaps://dc.clockwork.local:636`.
2. `add` de la cuenta en `LDAP_USERS_DN` con `userAccountControl = 514` (deshabilitada).
3. `modify` de `unicodePwd` (UTF-16LE entre comillas) por LDAPS.
4. `modify` de `userAccountControl = 512` (habilitada).
5. Lectura del `objectSid`, `dn` y atributos resultantes.
6. `INSERT` en `usuario`.

Si el `INSERT` falla, la cuenta recién creada se elimina de Samba AD para no
dejar huérfanos.

### Modificación (`CA-04`)

- `displayName`, `givenName`, `sn` y `mail` por `modify`.
- Contraseña opcional por `unicodePwd`.
- Estado por `userAccountControl` (512 activo / 514 deshabilitado).
- El `uid` y el `DN` no cambian.

Si la escritura en PostgreSQL falla, se intenta restaurar el estado anterior en
el directorio (compensación best-effort).

### Cambio de contraseña

El nuevo valor se aplica con un `modify` de `unicodePwd` por LDAPS. Para que la
contraseña anterior deje de ser válida de inmediato se configuró en el DC:

```ini
old password allowed period = 0
```

Sin este ajuste, Samba AD mantiene la contraseña anterior válida durante el
periodo de gracia (60 minutos por defecto), comportamiento heredado de AD.

### Desactivación (`CA-04`)

- `userAccountControl = 514` en Samba AD.
- `usuario.activo = false` en PostgreSQL.
- Se revocan las sesiones web activas (`sesion_web`), por coherencia con
  HU-COM-14 / CA-14.
- No se elimina la cuenta ni su historial.

## 6. Validaciones

| Campo | Regla |
|---|---|
| `uid` | 3–32 caracteres, `[A-Za-z0-9][A-Za-z0-9._-]*`, normalizado a minúsculas, inmutable tras el alta. |
| `email` | Formato válido, normalizado a minúsculas, único en BD y Samba AD. |
| `nombre_completo` | Obligatorio, máximo 255 caracteres. |
| `rol` | Uno de los cuatro roles del sistema. |
| `password` | Mínimo 8 caracteres y al menos 3 de: minúscula, mayúscula, número y símbolo. Obligatoria al crear; opcional al editar. |

Los duplicados se detectan antes de escribir y también con las restricciones
`uq_usuario_uid` / `uq_usuario_email` como última barrera.

## 8. Auditoría (RN-010)

Cada alta y modificación inserta en `auditoria`:

- `usuario_id`: actor autenticado.
- `accion`: `CREAR` o `ACTUALIZAR`.
- `entidad_afectada`: `usuario`.
- `entidad_id`: usuario afectado.
- `detalle`: `uid`, `email`, `rol`, campos modificados, cambio de contraseña y
  valores anterior/actual.
- `ip_origen` y `fecha_evento`.

La tabla `auditoria` es inmutable por trigger. La contraseña nunca se guarda ni
se registra.

## 9. Modelo de datos

No se requieren tablas nuevas ni columnas nuevas: `usuario` ya contiene `uid`,
`email`, `nombre_completo`, `rol`, `activo`, `samba_sid` y `samba_dn`, con
restricciones de unicidad.

La migración `db/migrations/03-hu02-auth-fk.sql` ajusta el trigger de
`evento_autenticacion` para permitir únicamente la anonimización de
`usuario_id` (`ON DELETE SET NULL`) al eliminar una cuenta, sin habilitar
`UPDATE`/`DELETE` generales sobre la auditoría.

## 10. Pruebas de aceptación

1. Alta válida → usuario en Samba AD y en PostgreSQL, con `samba_sid`/`samba_dn`.
2. Login del usuario recién creado → 200 (la contraseña se aplicó en AD).
3. Alta con `uid` duplicado en BD → 409 `UID_DUPLICADO`.
4. Alta con `uid` existente solo en Samba AD → 409 `UID_DUPLICADO_AD`.
5. Alta con `email` duplicado → 409 `EMAIL_DUPLICADO`.
6. Alta con rol inválido → 400.
7. Alta con contraseña débil → 400.
8. Edición de nombre/correo → reflejada en PostgreSQL y en Samba AD.
9. Cambio de contraseña → el login funciona con la nueva y falla con la anterior.
10. Desactivación → `activo=false`, cuenta deshabilitada en AD, sesiones revocadas.
11. Login de cuenta desactivada → 403 en la web / bind rechazado en AD.
12. Reactivación → la cuenta vuelve a autenticarse.
13. Docente intenta `POST /api/users` → 403 `ACCESO_DENEGADO`.
14. Admin Técnico puede crear y editar cuentas.
15. Cada alta/edición genera un registro en `auditoria`.
16. Intento de `UPDATE`/`DELETE` en `auditoria` → rechazado por trigger.

## 11. Configuración

```ini
LDAP_URL=ldaps://dc.clockwork.local:636
LDAP_BIND_DN=CN=Administrator,CN=Users,DC=clockwork,DC=local
LDAP_BIND_PASSWORD=...
LDAP_SEARCH_BASE=DC=clockwork,DC=local
LDAP_USERS_DN=CN=Users,DC=clockwork,DC=local
LDAP_CA_CERT=/app/certs/samba-ca.pem
LDAP_TLS_SERVERNAME=dc.clockwork.local
LDAP_TLS_REJECT_UNAUTHORIZED=true
```

Además, en `/etc/samba/smb.conf` del DC:

```ini
old password allowed period = 0
```
